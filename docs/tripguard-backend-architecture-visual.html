TripGuard Backend Control Plane

旅行知识库后端架构

后端不是简单调 LLM，而是把用户收藏和合作方官方抓取两条输入线，统一编排成可追溯、可归一、可检索、可引用的旅行知识库，再由 Agent 基于检索结果生成答案。

实体可归一
事实可追溯
回答可引用

用户收藏入库：从链接/长图到个人知识卡片

前端只负责采集入口和状态展示，后端完成解析、旅行相关判断、结构化抽取、实体挂载、chunk 与索引。

POST /sources/collect · /sources/collect-image
用户端输入 链接 / 分享文本 / 长图 App 负责采集、上传、展示状态。
合作方输入 官方渠道抓取任务 地图、公众号、旅游局、合作方数据。
用户问题 行程规划 / 推荐询问 目的地、天数、偏好、排除项。
API 接入层 FastAPI Gateway 鉴权、限流、任务创建、输入类型判断。
解析层 Parser / OCR / Platform Worker 网页正文、小红书、马蜂窝、长图 OCR、fallback。
定时任务 Crawler Job Orchestrator 抓取中台按目的地、POI、政策主题定期更新。
原始证据层 Source Documents 保留原文、URL、抓取时间、provider、hash。
AI 结构化 旅行相关 / 目的地 / 分类 / tags Gemma/Ollama 输出稳定 JSON schema。
实体归一 Canonical Entity Resolver 名称、外部 ID、地理、规则、LLM、人审兜底。
核心知识库 Entity / Relation / Facts 一个实体，多目的地挂载；事实带来源和版本。
检索材料 Chunks / Keywords / Embeddings 正文切片、关键词索引、向量索引。
用户资产 Cards / Itinerary Drafts 展示卡片、收藏状态、行程草稿。
问题理解 Intent Parser 目的地、天数、偏好、负向约束。
混合检索 SQL + Keyword + Vector hard filter、soft boost、放宽策略、rerank。
Agent 生成 Answer + used_sources 只基于检索上下文回答，不足时追问或说明不足。

后端关键难点

平台解析不稳定 不同平台短链、登录态、反爬、页面结构都不同，需要 worker 和 fallback。
实体归一 故宫、签证、路线都可能来自多个来源，必须归到稳定 canonical id。
事实冲突 多个官方源给出不同营业时间或政策时，需要优先级、版本和冲突状态。
混合检索 旅行检索不能只靠向量，目的地、分类、tag、关键词都要参与召回和排序。
引用约束 Agent 生成的每个推荐点都要能回到 source 或 fact，避免模型编造。
异步重试 解析、OCR、抓取、embedding 都可能慢或失败，需要任务状态和可观测性。
