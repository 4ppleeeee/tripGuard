# 测试用例生成

## 目标

根据评审通过的需求文档、接口文档和设计稿，生成可执行、可核验的测试用例集。

## 触发条件

用户提供以下输入时触发：

- 需求文档（迭代场景同时提供 diff）
- 接口文档（迭代场景同时提供 diff）
- 设计稿（迭代场景同时提供 diff）

注意：需求文档必需；接口文档、设计稿尽量读取，缺失时不中断，但在摘要中标记需人工评审。

## 输入

| 参数 | 说明 | 是否必须 |
|------|------|----------|
| 需求文档（基线） | 评审通过的基线需求文档 | ✅ |
| 需求文档（diff） | `docs/component/{模块名}/{页面名驼峰}/diff/{页面名下划线}_diff.md` | 迭代必须 |
| 接口文档（基线） | 基线协议文档 | 需人工评审 |
| 接口文档（diff） | `docs/component/{模块名}/{页面名驼峰}/diff/{页面名下划线}_protocol_diff.md` | 需人工评审 |
| 设计稿（基线） | `docs/component/{模块名}/{页面名驼峰}/{页面名下划线}.png` | 需人工评审 |
| 设计稿（diff） | `docs/component/{模块名}/{页面名驼峰}/diff/{页面名下划线}_diff.png` | 需人工评审 |

## 输出

- 测试用例集（含功能 / 边界 / 异常 三类）

## 执行步骤

### Step 0：模式判断

- 新建模式：无 `diff/` 目录或无 `{页面名下划线}_diff.md`
- 迭代模式：上述两者同时存在
- 处理：新建模式只读基线；迭代模式只对 diff 中新增/修改/删除产出增量用例并保存到 diff/
- 处理：进入迭代模式后，若协议/设计稿 diff 缺失，则标记为 `需人工评审`

### Step 1：读取与提取

| 文件类型 | 基线路径 | diff 路径 |
|---------|---------|-----------|
| 需求 | `docs/component/{模块名}/{页面名驼峰}/{页面名下划线}.md` | `docs/component/{模块名}/{页面名驼峰}/diff/{页面名下划线}_diff.md` |
| 协议 | `docs/component/{模块名}/{页面名驼峰}/{页面名下划线}_protocol.md` | `docs/component/{模块名}/{页面名驼峰}/diff/{页面名下划线}_protocol_diff.md` |
| 设计稿 | `docs/component/{模块名}/{页面名驼峰}/{页面名下划线}.png` | `docs/component/{模块名}/{页面名驼峰}/diff/{页面名下划线}_diff.png` |

迭代模式下命中“保持原样 / 无变化 / 不修改 / 沿用原设计 / 同基线”的条目不新增用例。

#### 删除类变更反向验证

diff 命中“删除 / 移除 / 下线 / 不再保留”时，必须新增反向验证用例，并至少包含以下 3 类断言：

- 目标入口或元素不可见
- 对应区域不可点击，或点击无效
- 旧链路不再触发

**优先级派发规则**：

- 删除原属 P0/P1 能力时，反向验证用例必须按 P0 处理
- 删除原属 P2 能力时，反向验证用例跟随原优先级

未生成反向验证用例时，必须在覆盖度检查与保存前自检中拦截，不得直接保存测试用例文档。

### Step 2：用例分类

#### 2.1 优先级判定

决策树：

```text
IF (核心业务流程) AND (影响用户完成关键任务):
  优先级 = P0
ELSE IF (常规交互) OR (边界条件) OR (常见异常):
  优先级 = P1
ELSE:
  优先级 = P2
```

**核心功能路径提取来源**：

| 来源 | 测试点 | 优先级 |
|------|--------|--------|
| 页面生命周期 - 进入页面 | 页面首次加载 | P0 |
| 页面生命周期 - 进入页面 | 页面首次加载失败提醒、重试 | P1 |
| 页面生命周期 - 加载成功 | 正常数据展示 | P0 |
| 页面生命周期 - 加载成功 | 数据展示异常的提示、重试 | P1 |
| 页面生命周期 - 退出/切换页面 | 页面切换、后台切前台、状态保存/销毁 | P1 |
| 互动组件 | 每个可交互组件的正常操作 | P0 |
| 互动组件 | 每个可交互组件的异常操作、提示、重试 | P1 |
| 动态组件 | 数据驱动的 UI 变化 | P1 |

**业务常见组件优先级参考**（避免跨项目漂移；冲突以本项目需求文档为准）：

| 组件/能力 | 默认优先级 | 备注 |
|-----------|------------|------|
| 视频播放（首屏、自动连播） | P0 |  |
| 评论发布、评论列表 | P1 | 涉及内容审核时升 P0 |
| 分享 | P1 | 跨端分享走兼容性 |
| 搜索入口 | P1 |  |
| 主题皮肤、字体大小 | P2 |  |
| 极端机型适配 | P2 |  |

#### 2.2 边界用例分类（子项清单见 5.4）

判定原则：服务可达 / 数据可控 / 操作合法但接近极值。覆盖维度包括空数据、临界数据、长文本、特殊字符、极端操作、组件边缘、弱网 Loading、Tab 切换、刷新机制、浮层/Toast 关闭路径。**子项清单与覆盖映射统一在 5.4 维护**，不在此处重复列出。

#### 2.3 异常用例分类（子项清单见 5.4）

判定原则：服务不可达、数据非法、权限受限、并发竞态、恢复路径。覆盖维度包括网络断开、接口超时、错误码、数据异常、权限异常、缓存异常、重试、异常恢复、**并发/竞态**（接口返回前连续触发、组件快速点击、跨组件同时触发）。**子项清单与覆盖映射统一在 5.4 维护**。

**匹配规则**：

- 关键词匹配 + 语义匹配，优先级 `精确 > 模糊 > N/A`
- 对“已匹配到本需求”的 checklist 行，必须细化到“检查点”粒度建立映射
- 多用例覆盖同一检查点不同子场景时全部进行合并；完全重复时仅保留优先级最高关联
- 允许 1 条用例覆盖多个检查点，也允许多条用例覆盖同一检查点
- 已匹配检查点必须按“、”拆分到子场景粒度逐个关联用例，不允许只在检查点整行层面笼统标记覆盖
- 已匹配检查点的每个子场景至少关联 1 条用例；未覆盖时必须回溯补齐
- 回溯后仍无法补齐时，标记 `需人工评审`，并写明无法补齐原因与建议补测方向
- 与本需求明确无关的检查点才可标记 `N/A` 并写明原因

### Step 3：BDD 生成

#### 3.1 模板

```markdown
- Feature:{功能聚类}
- TC-{编号}
- **优先级**:P0 / P1 / P2
- **所属模块**:{模块名} - {页面名}
- **关联需求**:{REQ:{锚点} / PROTO:{字段} / UI:{区域}}
-- Scenario:{用例标题}
--- Given {前置条件1}
--- And {前置条件2}
--- When {操作步骤1}
--- And {操作步骤2}
--- Then {预期结果1}
--- And {预期结果2}
--- When {后续操作步骤}
--- Then {后续预期结果}
```

**测试数据/账号要求**：Given 必要时写明执行所需账号或数据条件（例：`Given 主态登录账号 A（已实名）`、`Given 后端首页接口返回空列表`）。涉及主客态、新/老用户、黑产用户、未成年模式等多账号维度时**必须**写出，避免执行者口径不一。

#### 3.2 补充规则

- Feature 为第一层级，按需求功能聚类（如 UI / 功能；或 已登录 / 未登录）
- 每个用例都需要在优先级前增加一行 `TC-{编号}`
- Scenario 为第二层级，内容与当前用例标题一致
- Given 是否存在取决于是否有前置条件；无前置条件可省略
- 一个用例中可有多个 Given/When/Then；第一个使用 Given/When/Then，后续使用 And
- 协议字段必须翻译为业务语义后再断言。Agent 内部维护“协议字段 → 业务语义”映射（不在用例正文暴露），常见对照：

| 不允许（技术语） | 允许（业务语） |
|------------------|----------------|
| `isFinished=false` | “后端返回‘仍有更多剧集可加载’” |
| `dramaCardList 为空` | “未返回任何剧集卡片” |
| `FeedStyleType.DramaCards` | “卡片样式为‘剧集合集样式’” |
| `stGetFeaturedDramaFeedsRsp 失败` | “精选短剧 feed 拉取失败” |

- 必须保留字段值消歧时（如错误码），用“业务语义（字段值）”形式，例如“鉴权失败（错误码 401）”。

#### 3.3 去重与合并

- 用例间需去重，减少重复验证
- 去重必须“等价去重”：仅当验证目标相同时可合并；验证目标不同禁止合并删除
- 涉及滑动操作统一使用“上滑/下滑”

#### 3.4 When-Then 粒度

- When 拆到最小可执行粒度，每步仅描述一个动作并明确交互区域
- 单动作定义：单次用户交互（点击、输入、滑动等），不包含中间状态描述
- Then 与最近一组 When 逐条对应，给出可验证内容（文案、样式、状态、跳转）
- 边界场景需明确交互区域（如“点击头像和点赞按钮之前的区域”），并写清触发或不触发预期
- **允许同一 Scenario 内多组 When/Then 交替**（如 `When→Then→When→Then`），每组内部仍须满足“单动作 ↔ 可验证结果”对应；端到端链路用例使用此结构
- 每组 When 后必须有 Then；不允许只写操作不写结果

#### 3.5 Then 合并与保护

- 允许：同操作下、同维度的表述压缩
- 禁止：跨维度合并（可见性、状态一致性、排序、关闭路径、恢复时机、误触发防护）

#### 3.6 一致性与术语

- 同一条件下不得出现互斥预期（如同时“自动播放下一个视频”与“循环播放”）；分支预期必须显式补充分支条件（Given 或额外 When）后再写对应 Then
- 无法判定冲突时，标记 `需人工评审` 并注明冲突点
- 方位描述使用“组件 ID + 方位 + 条件”（例：`#12 + 左上角 + 有标签`）
- 优先保留端到端链路 Scenario，必要时再拆分子场景；核心流程至少保留 1 条完整链路用例，拆分仅用于可独立验证且不损失链路语义的场景
- 文案质量 Lint：错别字、术语不一致、中英文大小写异常需在交付前修正

#### 3.7 生成结果校验

- 每个用例必须包含：优先级、所属模块、关联需求
- 用例编号必须连续且不重复

### Step 4：用例生成结果复核

调用智能管家接口，进行用例生成结果复核。

#### 4.1 调用接口

- 调用接口：`http://21.91.251.179/seneschal/api/v1/pipeline/refine-testcases`
- `Content-Type`：`application/json`

接口参数：

```json
{
  "business_id": 7,
  "requirement_text": "{需求文档}",
  "initial_testcases": "{测试用例}",
  "features": [],
  "brain_hint": "",
  "business_type": ""
}
```

#### 4.2 接口返回信息处理

等待接口返回内容，如果超过 6 分钟没有返回结果，则认为检查失败，接口信息处理流程结束返回 `{测试用例}`，并显式标记为“未完成复核”。

如果在 6 分钟内返回结果，则认为检查成功，按以下规则处理接口返回内容。

##### 1. `test_cases` 的处理

新建模式下，`test_cases` 的处理：

- 根据 `test_cases` 中每条用例的 `refinement_action` 对已有 `{测试用例}` 执行新增、替换或保留。
- `refinement_action` 的值为 `added` 时，将 `test_cases` 下的内容拼接在已有的 `{测试用例}` 内容后，编号从基线最大编号后延续。
- `refinement_action` 的值为 `modified` 时，根据 `id` 将 `test_cases` 下的内容替换 `{测试用例}` 中相应的用例。
- `refinement_action` 的值为 `kept` 时，不改变与 `id` 对应的 `{测试用例}` 的内容。

迭代模式下，`test_cases` 的处理：

- `refinement_action` 的值为 `added` 时，将 `test_cases` 下的内容拼接在已有的 `{测试用例}` 内容后，编号从基线最大编号后延续。
- `refinement_action` 的值为 `modified` 时，不直接替换基线 `{测试用例}` 中的用例，提供“修改清单 + 新版用例”描述，供人工确认。

映射关系必须满足：

- `test_cases` 中的 `title` 对应 `{测试用例}` 中的 `{用例标题}`。
- `test_cases` 中的 `bdd_steps` 下的内容分别对应 `{测试用例}` 中的 `{前置条件}`、`{操作步骤}`、`{预期结果}`。
- `test_cases` 中的 `priority` 对应 `{测试用例}` 中的 `{优先级}`。
- `{测试用例}` 中的 `{所属模块}` 中的 `{关联需求}` 根据当前用例的内容解析出相关内容。

##### 2. `removed_cases` 的处理

新建模式下，`removed_cases` 的处理：

- 将 `removed_cases` 下的 `original_id` 对应的 `{测试用例}` 中的整条用例删除，并将编号按照顺序重新排序。

迭代模式下，`removed_cases` 的处理：

- 不删除基线文件，将 `removed_cases` 下的 `original_id` 对应的 `{测试用例}` 中的用例输出“删除清单”，供人工确认。

##### 3. 其他均无需处理，也不返回

##### 4. 最终输出要求

- 若接口成功返回，优先使用 `test_cases` + `removed_cases` 下的内容重组最终 `{测试用例}`，并标记为“已完成复核”。
- 新建模式复核处理完成后，最终输出必须按当前文档顺序重新连续编号为 `TC-001 ~ TC-n`；迭代模式不重排基线编号，仅新增编号从基线最大编号后延续。
- 若接口成功但 `test_cases` 为空且 `removed_cases` 为空，仍需输出复核前的 `{测试用例}`，并在结论摘要中说明“本轮复核未新增或保留正式问题”。
- 除非用户明确要求查看原始 JSON，否则不要直接原样回贴接口响应；必须转换为最终的用例格式。

#### 5.5 Checklist 子场景级校验

命中的检查点必须逐个子场景关联用例，并输出校验表。

```markdown
| 分类 | 功能 | 模块 | 检查点 | 子场景 | 覆盖用例 | 校验结果 | 说明 |
|------|------|------|--------|--------|----------|----------|------|
| 系统 | 网络条件变化 | 全场景 | 网络条件变化 | 弱网络 | TC-024 | ✅ 已覆盖 | — |
```

校验规则：

- `✅ 已覆盖`：该子场景已有明确 TC 关联，且用例 Then 可验证对应行为
- `❌ 未覆盖`：该子场景无 TC 关联，必须回溯补齐；无法补齐时改为 `需人工评审`
- `部分覆盖`：该检查点仅部分子场景有 TC 关联，说明列必须写明缺失子场景与补齐建议
- `需人工评审`：回溯补齐后仍无法覆盖，说明列必须写明原因与建议补测方向
- `N/A`：与本需求明确无关，必须填写说明
- 命中的检查点不得存在未处理的空白覆盖；发现 `❌ 未覆盖` 子场景时必须先回溯补齐，无法补齐再降级为 `需人工评审`

#### 5.6 删除类变更反向验证覆盖

若 diff 命中“删除 / 移除 / 下线 / 不再保留”，必须输出反向验证覆盖结果：

```markdown
| 删除项 | 原优先级 | 反向验证用例 | 不可见断言 | 不可点击/点击无效断言 | 旧链路不触发断言 | 状态 | 说明 |
|--------|----------|--------------|------------|-----------------------|------------------|------|------|
| {删除项} | P0 | TC-xxx | ✅ | ✅ | ✅ | ✅ 已覆盖 | — |
```

校验规则：

- 删除原属 P0/P1 能力时，反向验证用例优先级必须为 P0
- 3 类断言缺任一项时，状态必须为 `❌ 未覆盖`，并回溯补齐
- 无法补齐时，状态标记为 `需人工评审`，说明列写明阻塞原因
- 保存前不得存在未降级的 `❌ 未覆盖`

#### 5.7 输出排序

- 详细用例必须按 TC 编号升序输出，避免仅因重排产生大范围无效 diff
- 禁止仅调整顺序而不调整内容；若仅做排序优化，必须在变更说明标注“仅排序变更”
