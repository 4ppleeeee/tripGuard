# 一、需求前置检查

## 核心目标
仅基于**当前需求文档**（迭代时同时结合 `diff` 与基线文档）识别真正会影响设计、开发、联调、测试或验收的**业务定义问题**。
先输出检查报告，**不要直接改文档**；只有在用户确认修订范围后，才进入文档修订。


## 需求检查核心原则
本 skill 当前职责是：**先给检查报告，不直接改 spec**。
只有用户确认修订范围后，才进入文档修订。

### 1. 只基于需求原文做判断
- 所有正式问题都必须能回溯到当前需求文档中的具体描述、明确缺失或前后冲突。
- 不要根据“常见做法”臆造业务规则。
- 如果发现缺失，必须说明：**缺了什么、为什么影响落地、建议补什么**。

### 2. 先做分阶段检查，再汇总问题
必须严格按以下三阶段执行：
1. **Spec 文件上下文检查**
2. **缺陷反推检查**
3. **用例反推检查**

禁止一上来直接列问题清单；必须先完成阶段化分析，再输出总报告。

### 3. 只输出高价值问题
只有同时满足以下条件，才登记为正式问题：
- 与当前需求范围直接相关；
- 会影响设计、开发、联调、测试或验收；
- 能明确说明具体缺失点、冲突点或不确定点；
- 能给出明确修订方向或待确认决策点。

### 4. 问题必须是“业务定义问题”
以下情况**默认不算正式问题**：
- 没有单独的“互动组件描述”章节，但行为规则已经在别处说清楚；
- 没有“异常情况”小标题，但异常处理已散落在相关段落中并足够支撑实现；
- 组件清单、模块编号、章节目录没有一一对齐，但业务定义已完整表达；
- 缺少设计稿链接、附件、截图等辅助材料，但不影响当前需求判断。

只有当这些表面现象背后对应的是真实业务缺口时，才输出问题，而且必须写成业务问题，而不是写成文档结构问题。

### 5. 问题必须可定位、可修订、可验收


## 二、需求检查输入输出要求
### 触发条件
当用户提供以下任一输入时触发：
- 页面需求文档（`{page}.md`）
- 迭代差异文档（`diff/{page}_diff.md`）
- 希望从“是否能顺利设计 / 开发 / 测试 / 验收”的角度审视需求是否完整
- 指令包含“需求检查 / 需求评审前检查 / 漏洞式检查 / 边界场景检查 / 提测前需求自检 / spec 检查”等表达

### 输入
- **必填**：当前需求文档（新建：`{page}.md`；迭代：`diff/{page}_diff.md`）
- **条件必填**：迭代模式时基线文档 `{page}.md`。若未提供，则降级为“仅检查 diff 范围”，并在报告 §〇 显式声明“基线缺失，未做关联影响面检查”。
- 选填：设计稿说明、交互说明、历史争议记录、历史缺陷模式清单。


## 三、执行步骤

### step1：Spec 文件上下文检查
#### 阶段目标
判断当前 spec 是否具备进入后续设计 / 开发 / 测试讨论的基础上下文。

#### 必查项
围绕以下四类内容检查：
##### 1. 必备元素
结合需求内容，检查是否已描述清楚：
- 页面入口
- 页面目标与范围
- 互动组件描述
- 动态组件展示逻辑
- 关键流程及关键状态
- 关键异常情况描述
- 与其他页面 / 模块 / 入口的关系

注意：这里要求检查的是**是否有足够的业务定义**，不是检查文档目录是否一定存在这些标题。

##### 2. 逻辑冲突
重点识别：
- 前后规则是否矛盾；
- 同一状态在不同段落是否定义不一致；
- 展示逻辑、按钮态、数值口径是否冲突；
- 一处写“自动执行”，另一处写“用户手动触发”等互斥描述。

##### 3. 范围不一致
重点识别：
- 需求标题 / 目标 / 背景 与具体功能描述范围是否一致；
- 需求说是“仅改 A”，正文却引入了 B/C 的新逻辑；
- 目标写的是“展示优化”，正文实际包含了规则改造、状态同步等更深层改动；
- 页面职责、组件职责、入口职责是否越界或重叠。

##### 4. 描述模糊
重点识别：
- 存在模糊表述，例如“适当提示”“必要时展示”“按情况处理”“失败后兜底”；
- 文案缺失，导致用户可见结果不可判断；
- 数值要求、上下限、触发条件、排序规则、显隐条件未明确；
- 描述无法直接转化为代码规则或测试断言。

### step2：缺陷反推检查

#### 阶段目标
基于通用缺陷模式和历史高发风险，对需求进行“上线前反推式审查”，重点看未来最容易出错的地方是否已经在需求中写清楚。

#### 2.1 通用维度检查
至少检查以下通用维度：
- **主路径**：用户如何进入、触发、完成、退出
- **异常路径**：失败、取消、超时、权限不足、服务异常
- **边界场景**：空态、极值、重复操作、前后台切换、切页切 tab、外跳返回、冷启动恢复

#### 2.2 历史高发模块重点检查
当需求命中以下能力时，必须前置确认逻辑是否说清楚：
- 互动类：点赞、收藏、关注、评论、分享、追剧、订阅
- 状态类：加载态、成功态、失败态、恢复态、登录回流态
- 展示类：动态显隐、空态、错误态、弱网兜底、骨架屏、局部刷新
- 一致性类：多入口同能力、多页面同对象、多版本兼容、新旧逻辑并存
- 数据类：计数、排序、埋点、来源归因、实验分流、跨端同步

#### 2.3 风险补充
重点补查以下高风险模式是否已定义：
- 重复点击 / 连续触发策略
- 弱网 / 断网 / 超时重试策略
- 登录回流后的续执行或丢弃策略
- 跨入口状态同步策略
- 多页面 / 多tab / 多端同能力一致性策略
- 服务端回包与本地状态不一致时的收敛策略
- 恢复后状态对齐策略

### step3：用例反推检查

#### 阶段目标
从测试设计与业务场景覆盖的角度，反推需求是否足够支持用例设计、异常验证和验收落地。

#### 3.1 业务特有逻辑
根据需求是否命中，检查下列场景是否有定义：
- 端外分享回流
- 失败兜底
- 断网收藏 / 取消收藏反馈文案
- 恢复后状态对齐
- 登录前后行为差异
- 多入口重复操作
- 页面切换后未完成请求处理

#### 3.2 一致性检查
重点检查：
- 新旧版本展示与操作一致性
- 多入口同能力一致性
- 页面内外、主入口与二级入口一致性
- 术语与文案一致性
- 计数、状态、按钮态、显隐规则一致性

#### 3.3 可测性补充
每个关键需求点至少应当可以提炼出以下四元组：
- **触发条件**
- **系统行为**
- **用户可见结果**
- **验收口径**
如果某个需求点无法提炼出四元组，说明它通常仍然不够可开发或不可测试，需要登记问题。

#### 3.4 条件维度补充（命中才查）
仅当需求明显命中时，才补查以下维度：
- 兼容性
- 性能
- 安全与权限
- 可靠性
- 数据追踪
不要把所有条件维度机械套到每份需求上。

### step4：结构化输出 `{需求检查报告}`
将所有检查出的正式问题输出到 `{需求检查报告}` 中。

重要要求：
- 报告中**只返回正式问题列表**，不要添加结论摘要、总体结论、复核过程说明等额外内容。
- 如果最终没有正式问题，固定输出：`本轮未输出正式问题。`

#### 正式问题模板
正式问题必须使用 Markdown 表格输出，表头固定为：

```markdown
| 问题编号 | 问题标题 | 问题分析 | 修订建议 |
|---------|---------|---------|---------|
| ISSUE-001 | 双击播放区域的点赞语义未区分状态，存在误取消点赞风险 | 双击已赞视频通常不应触发取消点赞（仅播放飘心动画）。若按需求字面“等效于点击点赞按钮”实现，双击已赞视频将变成取消点赞，严重违背用户直觉与通用交互习惯。 | 明确双击播放区域的独立规则：未点赞时双击触发点赞并播放动画；已点赞时双击仅播放动画，不取消点赞，不改变计数。 |
```

### step5:需求检查报告复核
#### 调用智能管家接口，进行需求检查报告复核

##### 调用接口
调用接口：`http://21.91.251.179/seneschal/api/v1/pipeline/refine-requirement-analysis`

Content-Type：`application/json`

接口参数：
```json
{
  "business_id": 7,
  "requirement_text": "{需求文档}",
  "initial_analysis": "{需求检查报告}",
  "brain_hint": ""
}
```

##### 接口返回信息处理
等待接口返回内容，如果超过 6 分钟没有返回结果，则认为检查失败，会话结束返回 `{需求检查报告}`，并显式标记为“未完成复核”。
如果在 6 分钟内返回结果，则认为检查成功，按以下规则处理接口返回内容。

###### 1. `review_issues` 的处理
- 将 `review_issues` 视为复核后保留下来的正式问题数组。
- 必须按数组顺序遍历，每个元素输出为表格中的一行，**问题编号自增**。
- 最终报告必须使用以下表头，且列顺序不得调整：
  - `| 问题编号 | 问题标题 | 问题分析 | 修订建议 |`
  - `|---------|---------|---------|---------|`
- 每个数组元素与表格列的映射关系固定为：
  - `问题编号`：按输出顺序从 `ISSUE-001` 开始自增
  - `问题标题`：取 `title`
  - `问题分析`：优先取 `reason`；若 `reason` 信息不足，可结合 `description`、`risk_impact`、`evidence` 做 1~3 句补充，但核心结论必须与 `reason` 保持一致
  - `修订建议`：优先取 `suggestion`；若 `suggestion` 缺失或过短，可结合 `description`、`reason` 与证据补充为可执行建议
- `priority`、`phase`、`category`、`type`、`source`、`id` 等字段默认不单独输出，不要额外增加隐藏列或附加说明列。
- 除非用户明确要求查看原始接口字段，否则不要在最终报告中回贴 JSON 键名或原始对象结构。


###### 2. 其他字段默认不返回
- `weakened_issues`、`report`、`refinement_summary`、`duration_ms` 等内容，默认不进入最终报告。
- 只有当用户明确要求查看复核过程或原始返回值时，才可单独说明。

###### 3. 最终输出要求
- 若接口成功返回且 `review_issues` 非空，则直接按正式问题模板输出格式化后的 `{需求检查报告}`。
- 若接口成功返回但 `review_issues` 为空，则固定输出：`本轮未输出正式问题。`
- 除非用户明确要求查看原始 JSON，否则不要直接原样回贴接口响应；必须转换为最终报告格式。
