# UI 完整性验证 & 编译检查

## 目标
对照需求文档检查 UI 组件和功能是否完整实现，并验证 `androidApp` 模块编译是否通过。若 Android 编译失败，必须自动进入“定位错误 → 修复代码 → 重新编译”的闭环，确保交付代码在组件覆盖率和可编译性两方面均达标。

---

## 触发条件
- "检查 UI 组件是否完整"
- "验证编译"
- "编译检查"
- "验证 UI 和编译"
- Step 9（VM 实现编码）完成后自动触发

---

## 输入

| 参数 | 说明 | 是否必须 |
|------|------|----------|
| 需求文档 | 评审通过的需求文档（`docs/component` 目录下的 `.md` 文件） | ✅ 必须 |
| 实现代码 | 全部 UI 代码 + ViewModel 代码 + 页面入口代码 | ✅ 必须 |
| 基线需求文档 | 已有页面的完整需求文档（`{page}.md`） | 迭代模式必须 |

---

## 输出

- **UI 完整性检查报告**：组件覆盖率表 + 交互逻辑覆盖表 + 缺失项清单
- **编译检查报告**：编译结果 + 错误修复记录
- 全部通过后标记为 ✅

---

## 模式判断

```
CHECK: 当前页面目录下是否存在 diff/ 子目录，且其中包含 {页面名下划线}_diff.md？
  ├── YES → ✏️ 迭代模式：只检查 diff 涉及的组件和交互
  └── NO  → 🆕 新建模式：对照全量需求文档检查
```

---

## 执行步骤

### Step 1：读取需求文档，提取检查基准

从需求文档中提取：

1. **UI 组件清单**：所有区域的组件编号、名称、类型
2. **交互逻辑清单**：所有互动组件的触发条件和预期行为
3. **状态视图清单**：Loading / Error / Empty / 成功态等各状态视图
4. **动态组件逻辑**：受数据控制的显隐/切换逻辑

---

### Step 2：扫描实现代码，逐项核对

#### 2.1 组件覆盖率检查

逐一检查需求文档中的每个组件是否在 UI 代码中有对应实现：

```
对于每个组件 C in 需求文档.组件清单：
  1. 在 UI 代码中搜索对应的 Composable 函数/代码块
  2. 检查组件类型是否匹配（按钮/文本/图片/列表等）
  3. 检查组件是否绑定了正确的数据源（UIState 字段）
  4. 记录状态：✅ 已实现 / ⚠️ 部分实现 / ❌ 缺失
```

**输出格式：**

| # | 组件名称 | 状态 | 承载位置 | 备注 |
|---|---------|------|---------|------|

#### 2.2 交互逻辑覆盖检查

逐一检查每个交互是否完整实现：

```
对于每个交互 I in 需求文档.交互逻辑清单：
  1. 检查 UI 层是否有对应的事件监听（onClick / onSwipe / onRefresh 等）
  2. 检查事件是否 dispatch 了正确的 Action
  3. 检查 ViewModel 是否处理了该 Action
  4. 检查 UI 是否响应了 Action 产生的状态变更
  5. 记录状态：✅ 已实现 / ⚠️ 部分实现 / ❌ 缺失
```

**输出格式：**

| 交互 | 状态 | 说明 |
|------|------|------|

#### 2.3 状态视图检查

检查页面所有状态视图是否实现：

- [ ] Loading 加载中视图
- [ ] Error 错误态视图（含重试按钮）
- [ ] Empty 空态视图
- [ ] Success 成功态视图
- [ ] LoadMore 加载更多（如有分页）
- [ ] Refreshing 下拉刷新（如有刷新）

#### 2.4 动态组件逻辑检查

对照需求文档中的动态组件，检查控制逻辑是否完整：

- 显示/隐藏条件是否有代码实现
- 每条控制逻辑是否都有对应的状态判断

---

### Step 3：编译验证

#### 3.1 Metadata 编译

```bash
./gradlew shared:compileKotlinMetadata 2>&1 | grep -E "^e:|BUILD"
```

- 0 error → ✅ 通过
- 有 error → 记录错误，尝试修复

#### 3.2 Android App 编译

```bash
./gradlew androidApp:compileDebugKotlin 2>&1 | grep -E "^e:|BUILD"
```

- 0 error → ✅ 通过
- 有 error → **必须自动进入修复闭环，不要停在报错汇总**：
  1. 从编译日志提取首个确定性错误，优先处理真正阻塞编译的报错
  2. 优先修复本次改动直接相关的文件、import、类型、接口实现问题
  3. 每修复一轮后，重新执行 `./gradlew androidApp:compileDebugKotlin` 验证
  4. 直到 `BUILD SUCCESSFUL`，或确认被外部已有阻塞（如仓库中与本次无关的缺失实现/环境问题）卡住为止
  5. 若是外部阻塞，也要明确写出 **已自动尝试修复过**、**当前卡点文件/错误**、**为什么无法继续自动修复**

#### 3.3 Android 编译失败时的自动修复优先级

1. **本次代码引入的错误**：直接修复，不要留给后续处理
2. **本次任务范围内可安全补齐的缺失实现**：直接补齐并回归编译
3. **Pre-existing 错误**（非本次代码引入）：在不破坏现有结构的前提下，优先补最小桩实现 / 缺省方法 / 占位对象使编译通过
4. **环境或第三方依赖问题**：无法自动修复时，输出明确 blocker，并附已尝试动作

#### 3.4 错误修复策略

| 错误类型 | 处理方式 |
|---------|---------|
| 未解析的引用（本模块） | 检查 import、创建缺失文件 |
| 未解析的引用（跨模块） | 创建接口/桩实现 |
| 类型不匹配 | 修正类型声明 |
| KSP 生成代码问题 | 创建占位 object/class |
| 依赖不可用（模块无法访问） | 改用当前模块可访问的 API |

---

### Step 4：汇总报告

输出格式：

```
## UI 完整性 & 编译验证报告 - {页面名称}

### 一、组件覆盖率

| # | 组件名称 | 状态 | 承载位置 |
|---|---------|------|---------|
| 1 | xxx     | ✅   | XxxComponent.kt |
| 2 | xxx     | ❌   | — |

覆盖率：{已实现数}/{总数} = {百分比}

### 二、交互逻辑覆盖

| 交互 | 状态 | 说明 |
|------|------|------|

覆盖率：{已实现数}/{总数} = {百分比}

### 三、状态视图

| 状态 | 是否实现 |
|------|---------|

### 四、编译结果

| 编译目标 | 结果 | 错误数 |
|---------|------|--------|
| shared:compileKotlinMetadata | ✅ / ❌ | 0 |
| androidApp:compileDebugKotlin | ✅ / ❌ | 0 |

- Android 自动修复轮次：{N}
- 若仍失败：说明已自动尝试过的修复动作、最后阻塞点、阻塞原因

### 五、缺失项清单（需修复）

{列出所有 ❌ 和 ⚠️ 项}
```

---

### Step 5：修复缺失项

- 对于 **❌ 缺失的组件**：创建对应的 UI 代码
- 对于 **❌ 缺失的交互**：补齐事件绑定和 Action 处理
- 对于 **编译错误**：按 3.3 / 3.4 的自动修复闭环处理，不能只记录不修
- 每完成一轮修复后，都要重新执行 Step 3 验证编译

---

### Step 6：最终确认

所有组件覆盖率 100%、交互逻辑覆盖率 100%、编译通过后，输出：

```
✅ UI 完整性 & 编译验证全部通过
- 组件覆盖：{N}/{N} (100%)
- 交互覆盖：{M}/{M} (100%)
- Metadata 编译：✅ BUILD SUCCESSFUL
- Android 编译：✅ BUILD SUCCESSFUL
```
